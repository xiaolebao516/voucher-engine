# voucher-engine 项目交接上下文与新手进阶路线图

> **给后续接力模型（如 Hydrogen）的强制教学指令**：
> 1. **用户画像**：后端工程实操新手。有一定理论与面试“八股”基础（如知道分布式锁防误删、Fencing Token、退避重试等概念），但**缺乏把理论落到具体框架 API、配置文件和完整代码流程里的实操经验**。
> 2. **教学风格**：
>    - **自然引入新概念**：遇到 JUnit 并发测试、MDC、DLX、Outbox 等工具或术语时，先用一句生活化白话讲清“它是干嘛的、解决什么痛点”，再讲原理和代码，禁止一上来就甩专业名词或大段未解释的代码。
>    - **拒绝顺从与吹捧**：不要动不动说“你说的全对”。如果用户的代码推理或并发假设有逻辑漏洞，直接、温和但明确地指出来并纠正。
>    - **小步快跑**：一次只聚焦修 1 个问题或学 1 个机制，确保用户能独立理解并写出代码，再进入下一个。

## 一、 项目现状与真实底细

### 1. 已完成的核心功能与压测基准
- **业务场景**：高并发优惠券秒杀与核销系统（Spring Boot + MySQL + Redis + RabbitMQ + Docker Compose）。
- **核心链路**：
  1. 热点券查询：布隆过滤器防穿透 + Redis 逻辑过期 + 后台线程池异步重建。
  2. 抢购主链路：Redis + Lua 原子预扣库存与一人一单去重 $\rightarrow$ 投递 RabbitMQ 异步下单。
  3. 异步落库与超时退库：手动 ACK + 消费防重表 + TTL 延迟队列与死信交换机（DLX） + MySQL CAS 状态机退库存。
- **控制变量压测实测数据（本地单机，1,000 并发抢 100 张券）**：
  - **V1 纯 DB 乐观锁 (`seckill-db`)**：`520.0 QPS`，平均耗时 `313ms`，`$P99 = 1020\text{ms}$`，严格 100 单零超卖。
  - **V2 Redis + Lua + MQ (`seckill`)**：`1604.8 QPS`（吞吐提升 3.08 倍），`$P99 = 309\text{ms}$`（延迟降低 70%），严格 100 单零超卖。

### 2. 关于“黑马点评原版 vs AI 生成遗留问题”的坦诚说明
- **黑马点评原版确实更粗糙**：原版教程使用的是 Redis Stream 而非 RabbitMQ，根本没有消息防重表、超时自动退库、死信队列、本地压测对比，而且原版里一样直接用了 `Executors.newFixedThreadPool`（无界队列）和简化的缓存锁。
- **当前代码里暴露的 6 个 P0 Bug 确实有 AI 阶段性省略和疏漏的责任**：例如 `updated == 0` 只打日志不抛异常、消费端关闭重入队却没配下单队列死信交换机、Docker Compose 里配置了 `allkeys-lru` 淘汰策略、MQ 投递失败缺少 Lua 逆向回滚。这些是前面为了快速跑通第一版 MVP 时留下的简化与疏漏。
- **工程视角看待这件事**：真实软件工程本来就不是第一版就零缺陷的。把这些真实的 Bug 亲手挖出来、搞懂为什么错、自己修好并用测试证明修对了，比直接抄一份“看起来完美但自己看不懂”的代码更有面试含金量。

## 三、 新手概念白话速查与本轮纠偏记录

### 1. 两个新工具的白话解释
- **什么是 JUnit 并发测试？**
  - 平时你验证接口对不对，要么手动点接口，要么开 JMeter 配半天界面。**JUnit** 就是 Java 自带的“自动化测试按钮”，点一下就能跑一段验证代码。
  - **并发测试**就是在 JUnit 里写个大约 30 行的测试方法，用一把“发令枪”（`CountDownLatch`）让 50 个线程在**同一毫秒**同时调用你的抢券或核销方法，跑完后代码自动检查 `库存 == 0` 且 `订单数 == 10`。以后每次改完 Bug 点一下绿三角，2 秒钟就能确认有没有改坏，还能精准模拟“核销和超时退单同时撞车”这种靠手点根本测不出来的场景。
- **什么是日志追踪 ID（MDC TraceId）？**
  - 1,000 个人同时抢券时，IDEA 控制台里打出来的日志全混成一锅粥；更麻烦的是，抢券请求跨了 HTTP 线程 $\rightarrow$ 异步线程池 $\rightarrow$ RabbitMQ 消费者，根本看不出哪几行日志属于同一次下单。
  - **TraceId** 就像给每个请求进门时贴一张**“快递单号”**（比如 `a8f92b`）。**MDC** 是日志框架自带的一个“小口袋”，把单号塞进去后，这根线程里所有的 `log.info` 都会自动带上 `[a8f92b]`；跨线程和发 MQ 时顺手把这个单号传过去，以后排查丢单或报错，按单号一搜就能看到这笔订单从出生到退库的全程轨迹（就像查看 Agent 的 Trajectory 一样）。

### 2. 本轮代码排查中的 3 个关键纠偏
1. **纠偏一：为什么防重表插成功了，订单表还是可能报 `DuplicateKeyException`？怎么区分？**
   - **误区**：以为先插幂等防重表，冲突一定在前面就被拦了，不会走到订单表。
   - **真相**：两张表的唯一约束管的是**两件完全不同的事**。
     - 消费防重表（`tb_mq_consume_log`）按 `msg_id` 唯一，防的是**“同一条 MQ 消息被重复投递”**。
     - 订单表（`tb_voucher_order`）按 `(user_id, voucher_id)` 唯一，防的是**“同一个用户拿到两张相同的券”**。
   - **触发场景**：如果因为 Redis 内存淘汰（`allkeys-lru`）或重启导致已购 `Set` 丢了，同一个用户再点一次抢购，系统会生成一个**全新的 `msg_id`** 发往 MQ。此时防重表能顺利插入（因为 `msg_id` 是新的），但插订单表时就会撞上 `(user_id, voucher_id)` 唯一索引抛出 `DuplicateKeyException`！
   - **区分办法**：不需要去解析报错字符串，最干净的做法是**不要把两段插入包在同一个 `try-catch` 里**——给防重表单独包一个 `try-catch`（抓到说明消息重复，直接 ACK 忽略），给订单表单独包一个 `try-catch`（抓到说明业务重复下单，回滚并按业务异常处理）。

2. **纠偏二：`OrderTimeoutConsumer` 里 `SREM` + `INCR` 为什么要合进 Lua？**
   - **误区**：以为不加 Lua 时两个线程会同时 `SREM` 成功并都执行 `INCR`，导致“少卖”。
   - **真相（两点修正）**：
     - 第一，Redis 单条命令本身是原子执行的，两个线程同时对同一个 `userId` 执行 `SREM`，**必定只有一个返回 `1`、另一个返回 `0`**，不会同时成功。
     - 第二，就算真的发生了两次 `INCR`，库存多加了一张，后果是**超卖（资损）**，而不是少卖。
     - 第三，真正需要用 Lua 把 `SREM` 和 `INCR` 合并的原因是**防止两条命令之间进程崩溃**：如果 `SREM` 刚把用户删掉返回 `1`，还没来得及执行 `INCR` 程序就断电了；重启重试时再调 `SREM` 会返回 `0`（因为已经删了），代码以为退过了就跳过 `INCR`，这才真正导致了**库存永久少 1 张（少卖）**。合进一个 Lua 脚本后，这两步要么全执行，要么全不执行。

3. **纠偏三：关于 `OrderTimeoutConsumer` 里 SQL 退库存失败后直接 ACK**
   - 你的理解是对的：一旦调用了 `channel.basicAck`，RabbitMQ 就彻底删除这条消息了，永远不会再重试。所以如果 `refundOrderInDb()` 返回 `false` 是因为“上次崩溃前 MySQL 已经改成了 `status = 3`，但 Redis 还没来得及退”，直接 ACK 就会永久跳过 Redis 恢复。解决方法是返回 `false` 时查一下订单当前状态：如果是 `2`（已核销）才直接 ACK；如果是 `3`（已超时取消），就放行继续去执行幂等的退库存 Lua 脚本。
